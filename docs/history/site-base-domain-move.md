# Migration plan: user sites move from simple-host.app to simple-host.site

Nothing was changed while making this plan. I read only origin/main (fetched today, head `84701fb`), the live cert state directory, the service unit and `/etc/nginx/sites-available/simple-host`. I did not open the content-host nginx file. The plan includes your answer that simple-host.site is on Vercel DNS in the same team, so the existing DNS token and certificate hooks already work for it.

## Summary for the owner

1. Every person's page and every site gets a new address on simple-host.site, for example `madurai-idly.vineetu.simple-host.site`. Free names move too (`clay.simple-host.site`). The dashboard, sign-in, the connector (/mcp), the API, docs, setup, costs and enterprise pages stay on simple-host.app.
2. Every old simple-host.app address keeps working forever. It permanently redirects (301) to the same page on the new address, with path and query kept. That includes old `sites.simple-host.app/...` links and preview links.
3. Custom domains keep working with no change for anyone. Their DNS instructions keep pointing at simple-host.app, which is correct.
4. What visitors will notice: anyone signed in on a site is signed out once and signs in again on the new address. Anything a page kept only in the browser (game progress, drafts, "remember me" settings) starts empty at the new address. Everything saved on the server moves with the site. This is the same trade-off you accepted on 2026-09-25 and 2026-09-26.
5. People who self-host, run a hackathon box, or use Enterprise are not affected. They keep one domain unless they choose otherwise.
6. We roll out in small steps, and each step can be undone with one setting. The order is:
   - set up the new domain's DNS and certificates
   - serve both domains side by side
   - start handing out the new addresses
   - turn on redirects: temporary for a week, then permanent
   - update the skills and plugins
   - register with Google Search Console and the Public Suffix List
7. My advice is to wait until about 2026-10-28 before handing out the new addresses. Many company and school web filters block domains registered less than 30 days ago, and simple-host.site was registered today. Also, `.site` has a weaker reputation than `.app` with some filters. That is a known cost of the choice.
8. No Google sign-in settings change. Google always returns people to simple-host.app, which stays put.
9. Things only you can do:
   - Renew simple-host.site so it is paid at least two years ahead. The Public Suffix List requires this.
   - Verify the new domain in Google Search Console.
   - Open the Public Suffix List pull request.
   - Approve each step before it happens.
10. The new domain also gets its own certificate allowance from Let's Encrypt, 50 new certificates a week. Re-issuing today's 34 people takes about two days. Once it is on the Public Suffix List, that cap stops applying to people's addresses.

## 2. Design decisions

1. **Config: `SITE_BASE_DOMAIN`, defaulting to SITE_DOMAIN, plus `SITE_BASE_MOVE` and `SITE_BASE_CERT_DIR`.** SITE_DOMAIN keeps meaning "the app". The old base is always SITE_DOMAIN, so no extra list is needed. When base = SITE_DOMAIN, every code path is today's code path. The mode names mirror the PERSON_HOSTS and SITE_HOSTS pattern the owner already knows:
   - `serve`: both domains answer; addresses handed out stay .app
   - `canonical`: .site is handed out; .app still serves pages
   - `redirect`: .app pages 302 to .site
   - `permanent`: 301
2. **Redirects live in Go, not nginx.** Only Go knows:
   - whether a person's .site certificate is ready
   - that /v1/ must not redirect
   - aliases, renames and pinned sites
   - how to flip 302 to 301 with one setting and no nginx edit

   It is also the only way to avoid touching the forbidden content-host file. nginx gets one new file for .site and no edits to the existing ones.
3. **The redirect is a pure host-suffix swap, which makes a permanent 301 safe forever.** The label namespace is identical on both domains, so `anything.simple-host.app/p?q` → `anything.simple-host.site/p?q` never becomes wrong. The only exception is a two-label host whose .site certificate is not ready. That case gets a 302 with no-store to the .site person path, and that response is never cached.
4. **Free names move too.** They are user content, which is the whole point of the move. Stored rows are rewritten by C3, lookups accept both forms forever (C1), and new claims written as `.app` are accepted and stored as `.site`.
5. **The .app redirects last forever.** Keep renewing the 34 existing `*.<handle>.simple-host.app` certificates and the .app wildcard, and keep the .app DNS records. Stop issuing new .app per-person certificates at canonical: people who sign up later never had .app addresses. The cost is about 34 renewals every 60 days.
6. **`sites.simple-host.app` stays on .app** as the old-link redirector, the /v1/ API for old pages, and the host for the pinned eb2-wait. No `sites.simple-host.site` (it is reserved). Moving eb2-wait later follows step 4 of the nginx design doc.
7. **/v1/ is never redirected on old hosts** (D6).
8. **Apex `simple-host.site` 301s to simple-host.app.** This is the github.io pattern and gives the Public Suffix List a clean apex.
9. **Hand-made .app vhosts** (gods-eye, sf-fog, *.lab and the rest) are your own trusted sites. Leave them now and decide later.
10. **HSTS.** The .app TLD is HSTS-preloaded; .site is not. The global `Strict-Transport-Security: max-age=63072000; includeSubDomains` already applies to the new server blocks as long as they add no `add_header` of their own, and the port-80 servers redirect to https. Submitting to hstspreload.org (adding `preload`) is optional, after a month of stability. It is effectively irreversible, which is fine because .site will always be HTTPS.
11. **Cookie and storage effects, in plain words for the owner:**
    - Visitors signed in on a site are signed out once.
    - Browser-only data on a site (localStorage, IndexedDB) does not carry over. No safe general way exists to copy it, because the redirect happens before any page code runs.
    - Server-saved data, lists and private collections move untouched.
    - The owner's dashboard key is on simple-host.app and is not affected.
    - Show the note the owner app already uses ("sign-ins and browser-kept data start fresh on the switch") again for this move.
12. **Security review before shipping** C5, C4, D2, D3 and D8 (CLAUDE.md hard rule: OAuth, sessions, origins).

## Review notes (issues this plan checks for, found while reading the code)

- `auth.js` compares the page host with the auth apex. Under split domains, person-path pages would call the wrong API. Fixed in D8.
- `isRejectedPlatformHost` protects only the .app suffix. Without C5, unclaimed .site names would fall through to custom-domain proof checks instead of being refused outright.
- Cert readiness is keyed by handle alone. Reusing one ready directory for two zones would hand out .site hosts with no certificate. Hence B6 and F3 use separate state per zone.
- The certbot deploy hook reads a fixed conf. Renewals of .site lineages would be ignored ("not one of ours") unless the hook picks the zone from the lineage (F3).
- Free names are stored as full hosts in three columns. Lookups that accept both forms (C1) make the data rewrite and any rollback independent of each other.
- Today's content-host redirects are 302. The owner's 301 requirement is met at the `permanent` stage after a soak, matching the existing design doc.
- simple-host.site currently resolves to Vercel's parking IPs, so F1 must replace (not add to) the apex and wildcard records.

## As built (Release A, 2026-09-29): where it differs from the plan above

- **Served text instead of a host rewriter on simple-host.app (G1, G4).** The embedded pages, `llms.txt`, the OpenAPI spec, the ask packs, the AI-create prompt and the connector's text name people's addresses under `simple-host.site` in source. They are served with `simple-host.site` swapped back to `simple-host.app` until the hosted service hands the base out (`SITE_BASE_MOVE` canonical or later), and always on other installs, so today's bytes and headers are unchanged: the swap happens under the file server (`basetext.go`), and the host rewriter keeps its old shape (nil on simple-host.app). A test checks that every served file is the source with the swap applied; the text agent's invariant was that swapping back gives the previous file byte for byte. Old-link wording ("old `<handle>.simple-host.app/<site>/` links …") and the hackathon examples stay `.app`. The privacy and terms sentence "sites are served on simple-host.site" is left for the docs release (new text would change today's pages).
- **auth.js (D8)** keeps today's bytes. While the base moves, the served copy's person-host test covers a one-label host under either base (a line patched at serve time; a test fails if that line changes in auth.js, and `web/auth-base.test.js` runs both copies in node).
- **Free names are stored in the handed-out form (B11).** A claim under either base is accepted; it is stored under `.app` until canonical and under `.site` from then on. Lookups accept both forms (C1), so `move-site-base --apply` can run at any step; running it with the canonical switch (step 3) keeps every `domain` the API returns on `.app` during serve. The namespace lock is keyed on the handed-out form.
- **Nested bases are refused**: a `SITE_BASE_DOMAIN` under `SITE_DOMAIN` (or the reverse) is ignored with a warning.
- **The base's apex, www and reserved names** (`sites.`, `cname.`, …) answer 301 to the app in Go as well as in nginx.
- **Certificate requests** go to `SITE_BASE_CERT_DIR` from serve on and stop for `SITE_CERT_DIR` from canonical on. A split base with the move on refuses to start without `SITE_BASE_CERT_DIR` (and its `ready/` and `requests/`), since without it every person would count as ready under the base.
- **Scripts**: the site-certs issuer takes a conf path (`issue.sh [conf]`, per-instance lock `/run/<basename of STATE>.lock`), and a conf given as an argument must set `SITE_DOMAIN` and `STATE`; the deploy hook picks the instance by lineage suffix from `/etc/simple-host-site-certs.conf` and `/etc/simple-host-site-certs-*.conf`; the `.site` service has `ConditionPathExists=/etc/simple-host-site-certs-site.conf`; the drop-in's new line is `ReadWritePaths=-/var/lib/simple-host-site-certs-site/requests` (the `-` lets simple-host start before the directory exists). The nginx script backs up to `/var/backups/nginx-site-base-domain-<ts>/`, and its `/internal/` lock is `location ^~ /internal/ { internal; return 404; }` so the existing lock script reports 0 changes.
- **Not in Release A**: the showcase redirect (E3), the skills 0.28.0 bump and plugin text (G5), the Public Suffix List retarget (G8) and README/ARCHITECTURE text (G7) come with the later steps.
