Sites and versions

Every publish is a new version. The owner can publish without going live, open a preview link to any kept version, make it live, roll back, rename a site (old links keep working), take it offline, put a passcode on it, and download a copy with its saved data. A deleted site waits in Recently deleted (see Cleanup and retention).

Size. MAX_ARCHIVE_MB bounds one upload and one site. It is a guard against one upload filling a disk, not a budget: the median site on simple-host.app is about 25 KB. A proxy in front needs its own body limit raised to match. MAX_ARCHIVE_MB_OVERRIDES gives named accounts their own size; it holds new deploys only, so a larger site already live stays up. The admin page shows each site’s live copy (what the limit is about) and its total on disk (with kept versions).

Versions kept. Every version is a full copy of the site, so on a small disk the history, not the sites, is what fills it. The installer keeps one version (no rollback). Hosted Simple Host keeps 4; selected accounts default to 10. Only operator-allowed accounts can change their per-site count.

Hosted new sites from the 2026-10-05 deployment have a 200 MB whole-file allowance, and accounts have 1 GB. Earlier sites have no total cap. The live copy and retained versions count; backend storage stays separate. Checks use the resulting total after pruning. Self-hosted defaults have no account or site-total cap. See Website files and versions for exceptions and compression tips.

Site passcodes. An owner may put one passcode on a whole site. Every address of the site then shows a plain “This site is protected” page until the visitor enters it; a right passcode lets that browser in on that one address until the passcode changes or the owner signs everyone out. SITE_PASSCODES switches the feature; it also needs PASSCODE_ENC_KEY and a per-site address (SITE_HOSTS and PERSON_HOSTS on). A server where every site shares one address (a small box, an event box) refuses passcodes, because an unlock there would cover every site. Generate the key once with openssl rand -base64 32 and keep it secret like ADMIN_API_KEY: it seals every stored passcode so owners can read theirs back. Changing or losing it makes every stored passcode unreadable and signs every visitor out; owners then set new ones. PASSCODE_MIN_LENGTH is the shortest code allowed. Wrong tries are limited per address on a site (RATE_LIMIT_PASSCODE_IP, then PASSCODE_LOCKOUT_MINUTES) and per site from everyone together (RATE_LIMIT_PASSCODE_SITE, then PASSCODE_SITE_LOCKOUT_MINUTES); visitors already let in are not affected. A site with a passcode has a passcode file next to current in its folder, so addresses nginx or Caddy serve straight from disk hand the request to the app instead. The shipped vhosts and deploy/prod/nginx-suspended-marker.sh already do this; a hand-made nginx vhost that serves a site folder needs this line after its offline check:

if (-f <site folder>/passcode) { rewrite ^ /internal/passcode$uri last; }

and, when the block has no /internal/ proxy to the app, a location ^~ /internal/passcode/ one. nginx-suspended-marker.sh adds both to every block that serves a site folder.

Named viewers use the same marker and hand-off. An owner may open a whole site only to people named by email; each signs in on the site with that email (visitor sign-in, so the server needs email codes or Google set up), and the list is checked on every request. Like a passcode it needs a per-site address (SITE_HOSTS and PERSON_HOSTS on); a server where every site shares one address refuses it, because a sign-in there would cover every site. A site has named viewers or a passcode, never both. SITE_VIEWERS_MAX caps the list per site.

Recipes

The installer’s defaults already fit: --max-site-mb 100 --keep-versions 1. To cap each participant too:

MAX_SITES_PER_ACCOUNT=20

Keep rollback on a bigger disk. Install with --keep-versions 5.

Existing-site summaries after an upgrade

After upgrading to a release with zi-site-search-summary.sql and running migrate, populate summaries from the existing active site files. The command only updates sites without a summary, so reruns are safe. Run it in the app container, whose environment and site volume are already configured. No key or connection string needs to be copied.

Small-box installer and DigitalOcean installations:

docker compose --project-directory /opt/simple-host --env-file /opt/simple-host/.env run --rm --no-deps -T app site-summary-backfill

For either Coolify recipe, open the app service’s terminal after migration and run simple-host site-summary-backfill. For a manual Compose checkout, run docker compose run --rm --no-deps -T app site-summary-backfill from its directory. The old pinned releases do not contain this command; run it after installing the new release. New deploys populate summaries automatically.

Add photos

PHOTO_MAX_BYTES sets the maximum bytes per prepared photo (default 1,000,000). PHOTO_MAX_DIMENSION sets the longest allowed side in pixels (default 2048). PHOTO_MAX_CONCURRENT bounds photo saves across the process (default 3). PHOTO_BODY_TIMEOUT_SECONDS sets the body-read deadline at both the owner and photo-token entry points (default 60 seconds; positive integers). Unsupported response writers continue without a deadline. Both signed-in and token saves acquire a slot before reading the request body; full capacity returns 429 “Busy, try again in a moment” and Retry-After: 2 without queueing. A slot is held through commit. Each request still allows 30 photos of 1,000,000 bytes plus bounded multipart overhead by default. The Add photos page prepares small WebP or JPEG copies on the device. The server validates them without decoding pixels or resizing. Each request takes up to 30 photos; the normal site upload, retained-version, account, and deploy rate limits also apply.

Upload and import behavior

MAX_SITES_PER_ACCOUNT applies to non-admin accounts; exceeding it returns 403 site_quota_reached. Malformed MAX_SITES_OVERRIDES or MAX_ARCHIVE_MB_OVERRIDES entries stop startup.

MAX_ARCHIVE_MB caps the upload and its uncompressed live copy, excluding kept versions. Archive overrides apply on every deploy path, including admin deploys. Existing larger sites can still be rolled back to. /v1/me and GET /v1/admin/users report the account cap as max_site_mb; exceeding it returns 413 site_too_large. JSON and connector deploys carry base64, hence the proxy body allowance of 4/3 of the largest override noted in the table.

The upload pipeline and disk are sized for at most 50,000 files. When MAX_ARCHIVE_MB is set, the effective file cap is the smaller of MAX_FILES_PER_SITE and one file per 4 KB of that budget.

create_import_link creates a link spent by one import. The proxy must accept IMPORT_MAX_UPLOAD_MB request bodies on /v1/imports/. Up to five imports wait behind the concurrent conversions; further requests ask the person to try again in a few minutes. Downloaded import files include photos missing from the media file and theme stylesheets. Export links are reusable and may hold private collections, so their lifetime is capped at an hour.

The longest site passcode is 128 characters, independently of the configured minimum.
