Saved data

Deprecated, existing sites only. New sites use storage resources (KV, SQLite, files) — see storage-migration.md and storage-and-backups.md.

This page describes the existing state, collection and declared-kind API, which remains supported. New Simple Host sites may instead use owner-declared KV, SQLite and files resources with independent whole-resource read/write policies. See the storage migration plan before moving an existing site’s data; its private Submissions, Personal records, atomic operations and undo do not automatically map to a shared resource.

Every site gets a small backend in the same upload: one shared JSON document (page data) with atomic operations, and lists visitors add to (RSVPs, votes, sign-ups). A list can be private: only signed-in visitors add; the owner reads all, and each visitor reads their own.

Kinds. Each data name is one kind, and the kind decides who reads and who changes what: Page info (the owner writes, everyone reads), Submissions (visitors send entries; private to the owner by default; each visitor sees, changes and withdraws their own; an optional email digest to the owner), Personal (one private record per signed-in visitor) and Shared board (a list a group edits item by item). A name nobody declared is Shared, as before the kinds; SAVED_DATA_DEFAULT_KIND=declare_first makes new sites take no saves under an undeclared name. The owner can limit who may save on a site to listed emails and @domains, and block people. The SAVED_DATA_* settings below set each kind’s sizes and counts.

Undo. Every change to page data, and every deleted or edited list item, is kept for SAVED_DATA_UNDO_DAYS and can be restored by the site’s owner. History past its size cap is thinned oldest first, always keeping each item’s first change of every day. Unlike the dates in Cleanup and retention, shortening the undo window applies to what is already kept at the next sweep.

Limits. A site’s live saved data may not grow past SAVED_DATA_SITE_MAX_MB; writes that do not grow it always go through. Reads and list additions are rate limited per address.

The watch. The admin page counts, per site and day, the visitor writes a later step may tighten (still counted; not enforced yet), so an operator can see who would be affected first.

Who may write. WRITE_AUTH_MODE=on makes every page save need a signed-in visitor or the owner’s key.

Recipes

Shorter retention of saved-data history.

SAVED_DATA_UNDO_DAYS=7
SAVED_DATA_HISTORY_MAX_MB=5

Smaller per-site data on a small disk.

SAVED_DATA_SITE_MAX_MB=10

Turn on the comments preset (anyone posts after a spam check). The preset needs a Cloudflare Turnstile widget, which is free. Without both keys the server refuses the preset (400 spam_check_unavailable), the dashboard and the connector leave it out, and get_page_recipe sends guestbooks and comments to wall, where people sign in to post.

  1. In the Cloudflare dashboard, open Turnstile, choose Add widget, name it, and add this server’s own address as the hostname: the host of PUBLIC_BASE_URL (on a small box, the dashboard address, not the sites address). Widget mode Managed is fine.
  2. Copy the site key and the secret key into the server’s environment. On a small box installed with install.sh, add TURNSTILE_SITE_KEY=... and TURNSTILE_SECRET=... to /opt/simple-host/.env (re-running install.sh keeps both), then restart:
cd /opt/simple-host && sudo docker compose up -d
  1. The boot log says spam check: Turnstile on. Your sites, Manage, Storage now offers Comments. Under systemd, prefer TURNSTILE_SECRET_FILE with a credential over the plain secret.

Spam-check credentials

Without the Turnstile site key and secret, the comments preset is refused with 400 spam_check_unavailable. Its frame is /v1/turnstile/frame on PUBLIC_BASE_URL, whatever address the site uses. An unreadable TURNSTILE_SECRET_FILE turns the check off. A systemd credential can supply it: LoadCredential=turnstile-secret:/etc/simple-host-secrets/turnstile-secret and Environment=TURNSTILE_SECRET_FILE=%d/turnstile-secret.

Legacy saved-data behavior

SAVED_DATA_UNDO_DAYS applies to data already kept: shortening it removes older history and Recently deleted items at the next sweep, unlike the stored promises for site deletion and domain release.

The site owner restores history and deleted items. History thinning keeps each item’s first change of every day; it runs when a write crosses the cap (at most once a second per site) and in the sweep. The live-data cap excludes history and Recently deleted. Writes that grow it beyond the cap return 507 site_full; writes that do not grow it still succeed. Changes made with ops store only the change, with a full snapshot on the first change each day as well as at SAVED_DATA_SNAPSHOT_EVERY.

GET /v1/admin/data-watch reports the watch window. SAVED_DATA_WATCH_KEEP_DAYS must not be shorter than SAVED_DATA_WATCH_DAYS. Retries use Idempotency-Key. Owner-key and connector reads are limited per account rather than per address.

Page info (content), Personal (mine) and Shared board (board) oversized items return 413 item_too_large. The corresponding name caps, including Submissions (entries), return 409 too_many_names. Submissions and Shared board live-item caps return 409 list_full. Older Submissions entries up to 64 KB are kept. The Personal people cap counts Recently deleted records; a new person’s first save beyond it returns 409 people_full, while existing people keep saving. The per-person board write cap returns 429 and adds to SAVED_DATA_APPEND_PER_MIN, so one account on many addresses goes no faster.

Undeclared names in declare_first mode return 409 declare_first until the owner declares Page info or Submissions. Sites predating sd2-saved-data-kinds.sql stay Shared; every later site follows the current setting, so switching it changes all those sites. Shared keeps older skills and uploaded pages working. The “Email me: each” interval also sets how often due emails are checked.

Notification delivery behavior

The subscription cap counts agents and the dashboard together. Visitor events over the per-minute cap are not sent. Per-URL delivery limiting uses an in-memory token bucket with a one-attempt burst across all sites and subscriptions. Attempts are spread over about 15 minutes; 410 and 413 responses are never retried. Truncated string fields are listed under truncated. Oversized bodies omit fields, then cut visitor-controlled paths and keys to 256 bytes if needed. NOTIFY_DEFAULT_TTL_HOURS is also the maximum granted without an OAuth grant.

Image matching

See Image matching for PhotoDNA. These settings are forwarded by server (systemd) installs; Docker Compose does not pass them through yet. Without all three report identity fields, matches are recorded with report status off; the admin Report button appears once they are set. Evidence paths resolve symlinks, must be outside served paths and writable by the service (ReadWritePaths on a hardened unit). Exclude evidence from your own backups.
