Simple Host Enterprise installs into the company's existing Kubernetes cluster, with company OIDC sign-in and an existing S3-compatible bucket. Choose an existing Postgres or one persisted Postgres installed by the chart for evaluation. The helper downloads a standard Helm chart directory: Chart.yaml pins the Enterprise dependency under alias enterprise, values.yaml configures it under enterprise:, charts/ includes the published dependency archive, and README.md explains inspection, lint, rendering, client dry-run, install and upgrade. A secrets.env template stays blank; install.sh is optional. The same local chart can be rendered as Kubernetes YAML. It uses a persistent Kubernetes Secret so rendering and upgrades keep the same keys. Kubernetes, ingress, the bucket and the identity provider must already exist; the helper does not provision them. Chart configuration is provider-neutral and tunable through Helm values.

Addresses. An install lives at one address on its own registrable domain, like sites.example.com, never a subdomain of the company's main domain, so a published page can never read the company's cookies. Each person or team gets <owner>.<address> and every site its own origin. One wildcard DNS record covers every depth. Each owner needs a *.<owner>.<address> certificate: with certificates on auto, cert-manager issues them through a ClusterIssuer (an internal CA issuer is recommended; ACME needs DNS-01). TRUSTED_PROXY_CIDRS should name the ingress controller's pod range so rate limits and the audit log see real client addresses. With an AWS ALB there are no proxy pods: the ALB's own addresses in the VPC connect to the pods, so TRUSTED_PROXY_CIDRS is the VPC CIDR (or the ALB subnets' CIDRs), never the ALB controller pods' addresses. With an ALB, owner certificates are manual (OWNER_CERTS=manual, the owner-hosts component left out, an ACM certificate per owner plus DNS records for <owner>.<address> and *.<owner>.<address>, section 2 of the AWS page in the enterprise docs).

Sign-in. People sign in only through the company's OIDC provider (Okta, Microsoft Entra ID, Google Workspace, Keycloak or another); an account is created at first sign-in. There are no passwords and no admin key. Admins come from ADMIN_EMAILS or an OIDC claim (OIDC_ADMIN_CLAIM and OIDC_ADMIN_VALUE, refreshed at every sign-in). With Google Workspace, company email domains are required, or anyone with a Google account could sign in. The client is registered as a web application with the redirect URI https://<address>/auth/callback.

Sessions have an absolute limit (SESSION_TTL, default 8h, at most 24h) and an idle limit (SESSION_IDLE, default 30m, at most 8h). Simple Host checks the identity provider only at sign-in, so these are how long a leaver can keep working after being disabled there; disabling the person in the admin page ends everything at once. The install guide (INSTALL.md, Sessions and leavers) says to set both to match the identity provider's own session policy: when someone asks for that (say 12h and 1h to match Okta), it is the recommended setup, not a risk to argue against. Say it matches the guide, name the one caveat (a person disabled at the provider keeps working here up to that long, unless also disabled in Simple Host), and say to set them in Advanced, Accounts and sign-in; values longer than the defaults are typed there, not proposed. Matching sessions says nothing about which identity provider is picked: leave that answer alone. AI apps connect through the same sign-in and keep a short access token (OAUTH_ACCESS_TTL), refreshed until OAUTH_REFRESH_TTL. API keys for CI have a scope and an expiry (API_KEY_DEFAULT_DAYS, at most API_KEY_MAX_DAYS).

Access. Every site has one of five access levels: only me (the default), specific people and teams, the whole company, listed in the company showcase, or network (anyone who can reach it, no sign-in). Opening a site to the network needs an admin's approval, or two different admins' with NETWORK_ACCESS_APPROVALS=2. Teams are shared places for sites. ACCESS_LOG_VISIBILITY decides whether a site's owner sees counts (the default), who visited (owner), or nothing (admin).

Sites. Every publish is a new version; owners can preview, roll back, rename, move a site into a team and download it. Quotas apply per person or team (sites, and bytes across every kept version). With CLAMD_ADDR set every upload is scanned for malware. Each upload is held in the pod's memory, so MAX_ARCHIVE_BYTES times UPLOAD_CONCURRENCY must fit the pod's memory limit, and the ingress body-size limit must be raised with MAX_ARCHIVE_BYTES.

Cleanup and retention. A deleted site is kept whole for DELETED_RETENTION_DAYS; keep the bucket's old-version retention at least as long. Idle-site cleanup is off until IDLE_CLEANUP_DAYS is set (0 or at least 30); owners are warned on their dashboard, and by email when an SMTP relay is set, and get IDLE_CLEANUP_GRACE_DAYS to keep the site. The audit log, access log and search counts are pruned after their retention windows; audit retention is often set by company policy.

Finishing the install: after /readyz answers ok, INSTALL.md sections 8 and 9 are the definition of done: HUMAN STEP D (an admin signs in, confirms is_admin at /api/me, and mints a Full key on /dashboard; the admin's username may carry a suffix such as admin-2, since reserved names are never given out) and make smoke BASE=https://<address> KEY_FILE=<that key's file>. When owner certificates come from an internal CA, the machine running make smoke (and every browser) must trust that CA: set CURL_CA_BUNDLE to a file holding the system CAs plus the company CA.

Where the database is UpCloud's managed Postgres (the page fills in UpCloud's Postgres port when UpCloud is the bucket provider), use its public-... hostname.

Nothing on the page is required: an empty answer keeps its default or becomes a "# Fill in:" blank.

The chart supplies PORT, HTTPS_REDIRECT_PORT, OIDC_SCOPES and the other application defaults. The helper maps chart-owned settings to typed Helm values (such as enterprise.oidc.sessionTTL and enterprise.storage.sse); other settings go into extraConfig, and secrets stay in the existing Kubernetes Secret. Unknown values remain blanks and the files list what to fill in before installation. For external Postgres, supply its CA with --set-file enterprise.postgres.external.caCert=db-ca.crt. For in-cluster Postgres, choose a persistent volume size and StorageClass; nothing backs it up automatically.

Email is only for idle-site cleanup notices, through the company's SMTP relay; sign-in goes through the identity provider, so there are no sign-in emails.

Storage. Postgres holds accounts, sites, saved data and the audit log: use a managed Postgres with point-in-time recovery, reached over verified TLS. The bucket holds every site version and uploaded file, with server-side encryption and optionally a client-side envelope key; turn on bucket versioning. Pods are stateless. An existing identity supported by the AWS SDK credential chain can replace bucket keys. Configure enterprise.serviceAccount.annotations, enterprise.podAnnotations or enterprise.podLabels in values.yaml as the existing platform requires. Other S3-compatible stores use their access keys (GCS uses HMAC keys); native Azure and Google workload credentials are not supported by this S3 client.

Security. SECURE_MODE=true is required for a real install; the insecure and plaintext switches are for local evaluation only. Security-sensitive rate limits (sign-in, key minting, admin actions, OAuth) are stricter freely but at most four times looser than built in. Rate limits are <burst>/<interval>.

Sizing. No setting is tied to the number of people; quotas are per person or team, and busy dashboards read by many people may need a higher per-site read limit. Memory per pod follows MAX_ARCHIVE_BYTES times UPLOAD_CONCURRENCY, not the number of people.

Recipes from the settings docs:
- Stricter sign-in (a shorter working session, AI apps sign in again weekly, short-lived keys): SESSION_TTL=4h, SESSION_IDLE=15m, OAUTH_REFRESH_TTL=168h, API_KEY_MAX_DAYS=30, API_KEY_DEFAULT_DAYS=30, RATE_LIMIT_AUTH_EMAIL=3/2m.
- Two-person rule for network access: NETWORK_ACCESS_APPROVALS=2.
- Owners never see who visited: ACCESS_LOG_VISIBILITY=admin.
- Shorter retention: DELETED_RETENTION_DAYS=14, ACCESS_LOG_RETENTION_DAYS=30, SEARCH_TELEMETRY_RETENTION_DAYS=30.
- Clean up abandoned sites: IDLE_CLEANUP_DAYS=365, with IDLE_CLEANUP_MAX_EMAILS=200 so the first run does not send a flood.
- A busy dashboard read by many people: RATE_LIMIT_STATE_READ_SITE=600/100ms.
- Bigger sites: MAX_ARCHIVE_BYTES=262144000 (250 MiB), the ingress body size 250m, and more pod memory.
- Reserve hostnames: RESERVED_LABELS=intranet,vpn,hr.


Installation: inspect the downloaded Chart.yaml and bundled templates, then use README.md to lint, render and client-dry-run the local chart without applying resources. After review, create the namespace, fill secrets.env locally and create simple-host-secrets, then run helm install simple-host . from the chart directory. Later use helm upgrade simple-host .; dependency downloads are not required because the chart is bundled. .helmignore keeps filled credentials out of chart files. Helm or rendered YAML both set secrets.existingSecret. Generate signing and envelope keys once, keep them across upgrades, and back up the envelope key; otherwise existing encrypted site files become unreadable. Use the existing owning-role password with external Postgres and a different password for the application role. The page never receives these values. Select the intended kubeconfig context explicitly in every command. With manual certificates, supply the base TLS Secret and each owner’s wildcard certificate and ingress; automatic mode uses an existing cert-manager ClusterIssuer.
