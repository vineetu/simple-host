Simple Host Enterprise / Architecture

Describes release v1.1.0, coming soon. The current release on GitHub is v1.0.0.

How Simple Host Enterprise is built

Simple Host Enterprise is one Go service that runs in your own Kubernetes cluster. It serves static pages plus the data those pages save. Each person's pages live on their own hostname, so one person's page cannot read another's. Everyone signs in through your identity provider, unless an admin has opened a site to the whole network. Uploaded files are stored and served as bytes; they never execute on the server.

01.

Identity and addresses

Every request says who is asking, and every person's pages sit on their own browser origin.

  1. 1.1
    One sign-in, yours. People sign in through your identity provider — any OIDC provider: Okta, Entra ID, Google and others. The provider must vouch for the email address (email_verified), or sign-in is refused. There are no local accounts and no admin key. Admins are real signed-in people, named by an email list or a claim from your provider.
  2. 1.2
    A hostname per person. Each person's sites live under their own hostname, as paths: layla-hassan.<your domain>/tracker/. Different people are different browser origins, so one person's page cannot read another person's pages, storage or cookies.
  3. 1.3
    Sites for specific people get their own hostname. A site shared with named people or teams is served at <person>--<site>.<your domain>, for example oliver-bennett--roadmap.<your domain>. It is then apart from its owner's other sites too.
  4. 1.4
    Management stays on the base address. The dashboard, the API and the MCP endpoint are served on <your domain>. No hosted page is ever served there.
  5. 1.5
    Moving between addresses. The browser signs in once, at the base address. Opening a person's hostname hands the session over with a one-time code that expires after 60 seconds and is spent by its first use. Each host then holds its own __Host- cookie (Secure, HttpOnly), bound to that host and refused on any other.
  6. 1.6
    Changes need the right Origin. A change made with a browser cookie must carry the Origin of the address it was sent to. A page on one address cannot make changes on another.
  7. 1.7
    AI apps sign in as the person. ChatGPT, Claude and other AI apps connect to /mcp with OAuth: the person signs in through your identity provider and allows the app once. The app gets a one-hour access token and a rotating refresh token that carry that person's rights and no more. OAUTH_REDIRECT_HOSTS limits which apps can finish connecting. Each installation serves its own plugin, with its address already filled in.
  8. 1.8
    API keys are for automation. CI and scripts use an API key. Only a signed-in person can create one. Keys are stored as a hash, expire (90 days by default, 365 at most) and can be revoked. The admin API accepts a browser session only, never a key.
02.

File safety

Uploaded files are data. JavaScript can run in a viewer's browser; nothing uploaded runs on the server.

  1. 2.1
    No server-side execution path. Published files are stored and served as bytes with a content type. The server never evaluates them. Each published version is stored once in the bucket and never changed.
  2. 2.2
    Four archive limits. A publish request is capped at 100 MiB. Each file may be up to 500 MiB once extracted, the whole archive up to 500 MiB, and an archive may hold at most 50,000 entries. Each entry's size is checked before it is read. Files sent inline through MCP are capped at 8 MiB.
  3. 2.3
    Broad acceptance, small denylist. Any regular file is accepted, including ZIP and DMG downloads. Refused extensions: .sh .bash .zsh .fish .bat .cmd .ps1 .py .pyc .rb .pl .go .php .exe.
  4. 2.4
    Two confinement layers. Every path is reduced to a canonical relative path, and anything unsafe (../, an absolute path, a backslash) is refused. Separately, object keys in the bucket are built only from validated IDs, and each pod's local copy of the sites it serves is confined with Go's os.Root, so nothing can reach outside it.
  5. 2.5
    Files a page uploads are checked by their bytes. The files API accepts images, audio, video, PDF, plain text, JSON, CSV and archives, judged from the content, not the name. Nothing is ever stored or served as HTML. Defaults: 25 MiB per file, 500 MiB and 5,000 files per site.
03.

Who can see what

Every site has one of five access levels. A new site opens only for its owner, who decides from there.

Only meThe default for a new site. Only the owner can open it, or, for a team's site, the team's members.
Specific people or teamsThe owner names the people or teams who can open it. The site moves to its own hostname, and everyone else gets a 404, the same answer as a site that does not exist.
Anyone in the companyAnyone signed in who has the link. The link can be passed on, so this is not private.
ListedAnyone in the company, and the site appears in the company showcase and in search, credited to its owner.
Anyone on the networkNo sign-in. The owner asks for it with a reason, and the site keeps its level until an admin approves. Visitors who are not signed in can read its pages, files and saved data, and change nothing. The owner can lower the level at any time, and an admin can revoke it.
TeamsA team is a namespace, like a person. Every member can publish and manage its sites, which is how people work on a site together.
Saved dataAnyone who can open a site can read and write its saved data, as themselves. Writes go into the audit log under the person who made them.
LeaversOnce your identity provider stops an account, that person cannot sign in again. Open sessions end within the session lifetime: 12 hours, or 1 hour idle, by default. An admin can disable the account, which ends every session and revokes every API key and connected app at once.
04.

Records

Changes and visits are written down, where an owner or admin can read them back.

Audit logChanges to sites and access: publishing, updating, deleting and rolling back a site, access-level changes and network requests, approvals and declines, named viewers, team changes, saved-data writes, and file uploads and deletions. Also sign-in, refused sign-ins and sign-out, API keys created and revoked, and admin actions. A site change and its audit row are written in the same database transaction, and the row's time comes from the database clock.
Access logOne row for every hosted page served, the owner's and team members' own visits included.
Who reads themAn owner reads the audit log for their own sites and their teams' sites. From the access log they see views per day and how many different people visited, not who. An admin sees who, reads everything and can export it. A setting can instead show owners each visit, or hide the access log from everyone but admins.
Append-onlyThe database role the service runs as can add rows to both logs but cannot change or delete them. The service refuses to start if its role could change the audit log.
RetentionBy default, 400 days for the audit log and 90 days for the access log. A monthly job drops expired partitions.
Request logOne JSON line per request on standard output, with an ID returned as X-Request-Id.
Client addressesTaken from X-Forwarded-For only when the request comes through a trusted proxy (TRUSTED_PROXY_CIDRS, private ranges by default). The same address is used for rate limits and in every log.
05.

Runtime

One Deployment and one scheduled job in your cluster. Postgres, the bucket and sign-in are yours.

R1DeploymentTwo replicas. A rolling update starts a new pod before it stops an old one, a PodDisruptionBudget keeps one serving through node drains, and the replicas spread across nodes when there are several. Pods are stateless: sites live in the bucket, and Postgres decides which version is live.
R2Schema stepAn init container, migrate, runs the same image before the server starts. It takes a lock, applies pending migrations as the database's owning role, each in one transaction with its record, and exits. The server refuses a schema it does not know, unless every newer migration is marked backward-compatible, so an image can be rolled back without restoring the database.
R3Least-privilege roleThe server connects as simplehost_app, which can read and write application data but cannot change the schema or truncate tables.
R4HardeningThe namespace enforces the restricted Pod Security profile. Every container runs as a non-root user with a read-only root filesystem, all capabilities dropped and the default seccomp profile. No Kubernetes API token is mounted.
R5Pod storageEach pod keeps a bounded cache of the versions it serves in an emptyDir, emptied on start. /tmp is a second scratch emptyDir. A pod holds nothing that is not in the bucket or the database.
R6Ingress and metricsThe base address and a wildcard beneath it, on one TLS certificate, to one ClusterIP Service. Prometheus metrics are on a separate port, 9090, which the Service does not expose; scrape the pod directly.
R7Scheduled jobprune runs monthly as the owning role and drops expired log partitions. It touches only Postgres.
R8Your PostgresOver TLS with sslmode=verify-full; the service refuses to start otherwise. Point-in-time recovery is required: Postgres holds which version of each site is live, the saved data and the accounts, and nothing in the package backs it up. Every page request looks up the live version there, so the sites need it running.
R9Your bucketAn S3-compatible bucket over HTTPS is the site store: every version and uploaded file, written once. Bucket versioning with a lifecycle rule is required and is the backup for those files. Every object carries a server-side-encryption header, with an optional client-side envelope on top. The service refuses a plain-HTTP endpoint.
R10ReleasesRelease images are signed with cosign (keyless, from the release workflow) and carry an SBOM and a provenance attestation. There is no latest tag: the manifests pin an image digest, and the install check refuses the placeholder.
06.

Boundaries

  1. N1
    Not a server-side compute platform. Pages can run JavaScript in the browser. Nothing uploaded runs on the server.
  2. N2
    Not a secrets store. Anyone who can open a page can read what it saves. Keep secrets out of pages and saved data.
  3. N3
    Not a content scanner. Files are checked for size, path, extension and type, not for what they contain. The source is yours to extend if you want a scanner.
