Simple Host Enterprise / Architecture

How Simple Host Enterprise is built

Simple Host Enterprise is one Go service that runs in your own Kubernetes cluster. It serves static pages plus the data those pages save. Each person's pages live on their own hostname, so one person's page cannot read another's. Everyone signs in through your identity provider. Uploaded files are stored and served as bytes; they never execute on the server.

01.

Identity and addresses

Every request says who is asking, and every person's pages sit on their own browser origin.

  1. 1.1
    One sign-in, yours. People sign in through your identity provider — any OIDC provider: Okta, Entra ID, Google and others. There are no local accounts and no admin key. Admins are real signed-in people, named by an email list or a claim from your provider.
  2. 1.2
    A hostname per person. Each person's sites live under their own hostname, as paths: layla-hassan.<your domain>/tracker/. Different people are different browser origins, so one person's page cannot read another person's pages, storage or cookies.
  3. 1.3
    Restricted sites get their own hostname. A site with named viewers is served at <owner>--<site>.<your domain>, for example oliver-bennett--roadmap.<your domain>. It is then apart from its owner's other sites too.
  4. 1.4
    Management stays on the base address. The dashboard, the API and the MCP endpoint are served on <your domain>. No hosted page is ever served there.
  5. 1.5
    Moving between addresses. The browser signs in once, at the base address. Opening a person's hostname hands the session over with a one-time code that expires after 60 seconds. Each host then holds its own __Host- cookie (Secure, HttpOnly), signed for that host and refused on any other.
  6. 1.6
    Changes need the right Origin. A change made with a browser cookie must carry the Origin of the address it was sent to. A page on one address cannot make changes on another.
  7. 1.7
    Agents use keys. A coding agent calls the API or the MCP endpoint with an API key. Only a signed-in person can create a key. Keys are stored as a hash and can be revoked.
02.

File safety

Uploaded files are data. JavaScript can run in a viewer's browser; nothing uploaded runs on the server.

  1. 2.1
    No server-side execution path. Published files are stored and served as bytes with a content type. The server never evaluates them.
  2. 2.2
    Four archive limits. A publish request is capped at 100 MiB. Each file may be up to 500 MiB once extracted, the whole archive up to 500 MiB, and an archive may hold at most 50,000 entries. Each entry's size is checked before it is read. Files sent inline through MCP are capped at 8 MiB.
  3. 2.3
    Broad acceptance, small denylist. Any regular file is accepted, including ZIP and DMG downloads. Refused extensions: .sh .bash .zsh .fish .bat .cmd .ps1 .py .pyc .rb .pl .go .php .exe.
  4. 2.4
    Two confinement layers. Every path is reduced to a canonical relative path, and anything unsafe (../, an absolute path, a backslash) is refused. Separately, all file access is confined with Go's os.Root, so nothing can reach outside its site's directory.
  5. 2.5
    Files a page uploads are checked by their bytes. The files API accepts images, audio, video, PDF, plain text, JSON, CSV and archives, judged from the content, not the name. Nothing is ever stored or served as HTML. Defaults: 25 MiB per file, 500 MiB and 5,000 files per site.
03.

Who can see what

Nobody sees anything without signing in. Beyond that, the owner decides.

Signed in, alwaysEvery view of a hosted page needs a signed-in session. There are no anonymous visitors.
Unlisted by defaultA new site is not listed anywhere. Anyone signed in who has the link can open it, so unlisted is not private.
SharedWhen the owner shares a site, it appears on their hostname's index page, in the showcase and in search, credited to them.
Named viewersA site can list the people or teams allowed to see it. It moves to its own hostname, and everyone else gets a 404, the same answer as a site that does not exist.
EditorsThe owner can add editors to a site. An editor can publish new versions of it.
TeamsA team is a namespace, like a person. Every member can publish and manage its sites.
Saved dataA site's saved data follows the site: anyone who can open it can read and write its data, as themselves. Every write is recorded with who made it.
LeaversOnce your identity provider stops an account, that person cannot sign in again. Open sessions end within the session lifetime: 12 hours, or 1 hour idle, by default. An admin can disable the account, which ends every session and revokes every API key at once.
04.

Records

Every change and every visit is on record.

Audit logEvery change: publishing, updating, deleting and rolling back a site, changing who can see or edit it, team changes, saved-data writes, file uploads and deletions, sign-in and sign-out, API keys created and revoked, and admin actions. A site change and its audit row are written in the same database transaction.
Access logOne row for every hosted page served, the owner's and editors' own visits included.
Who reads themAn owner reads the records for their own sites and their teams' sites. An admin reads everything and can export it. The access log can be limited to admins.
Append-onlyThe database role the service runs as can add rows to both logs but cannot delete them.
RetentionBy default, 400 days for the audit log and 90 days for the access log. A monthly job drops expired partitions.
Request logOne JSON line per request on standard output, with an ID returned as X-Request-Id.
05.

Runtime

One Deployment, one volume and two scheduled jobs in your cluster. Postgres, the bucket and sign-in are yours.

R1DeploymentOne replica with the Recreate strategy, because the site volume is ReadWriteOnce.
R2Schema stepAn init container, migrate, runs the same image, applies the schema as the database's owning role, and exits. The server refuses to start unless the schema is exactly the one it expects.
R3Least-privilege roleThe server connects as simplehost_app, which can read and write application data but cannot change the schema or truncate tables.
R4HardeningThe namespace enforces the restricted Pod Security profile. Every container runs as a non-root user with a read-only root filesystem, all capabilities dropped and the default seccomp profile. No Kubernetes API token is mounted.
R5StorageOne ReadWriteOnce volume holds every site's files and uploads. /tmp is an empty scratch volume.
R6IngressThe base address and a wildcard beneath it, on one TLS certificate, to one ClusterIP Service.
R7Scheduled jobsbackup-assets runs hourly, mounts the volume read-only and copies uploaded files to the bucket. prune runs monthly and drops expired log partitions.
R8YoursPostgres over TLS with sslmode=verify-full. An S3-compatible bucket over HTTPS, which receives a backup of every published version, with a server-side-encryption header and an optional client-side envelope. Your OIDC provider. The service refuses to start if the database or bucket connection is not secured.
06.

Boundaries

  1. N1
    Not a server-side compute platform. Pages can run JavaScript in the browser. Nothing uploaded runs on the server.
  2. N2
    Not a secrets store. Anyone who can open a page can read what it saves. Keep secrets out of pages and saved data.
  3. N3
    Not a content scanner. Files are checked for size, path, extension and type, not for what they contain. The source is yours to extend if you want a scanner.
