# Changelog

One line per shipped change, newest first. Add a line here in the same commit as any feature change.

## Unreleased

- **Users list on the admin page.** A table at the top of `/admin` lists every account newest first: number, when they joined (date and how long ago), handle linked to their page, email, number of sites, and a muted "suspended" mark. Clicking Joined flips to oldest first. `GET /v1/admin/users` now also returns each user's `page_url`. No migrations.
- **The server refuses to start with the move on and no certificate hand-off for the new domain.** With `SITE_BASE_MOVE` on and `SITE_BASE_DOMAIN` different from `SITE_DOMAIN`, an empty `SITE_BASE_CERT_DIR`, or one without `ready/` and `requests/`, is now a startup error instead of a warning (it made every person count as having a certificate there). A Host with a trailing dot is treated like one without in the sign-in return check and the old-address redirect. No migrations.
- **Ready to move user sites to simple-host.site (dormant).** New settings `SITE_BASE_DOMAIN` (the domain people's and sites' addresses live under; default `SITE_DOMAIN`), `SITE_BASE_MOVE` (`off`, `serve`, `canonical`, `redirect`, `permanent`; default `off`) and `SITE_BASE_CERT_DIR`. With the move on, person, site and free-name addresses answer under both domains, the handed-out address switches at `canonical`, and old addresses redirect (same labels, path and query; 302, then 301 at `permanent`; `/v1/` never), while the app, sign-in, the API, emails, the content host and the CNAME target stay on `SITE_DOMAIN`. Lookups, the shared name namespace, visitor sign-in return addresses, origin checks (including an allow-listed origin's twin), analytics, the report form and the data download all treat a name under either domain as the same name. New `simple-host move-site-base --from A --to B [--apply]` rewrites stored free and retired names (dry run by default, idempotent). Deploy: `deploy/prod/nginx-site-base-domain.sh` (dry run by default) serves the new domain; `deploy/site-certs/` takes a conf per domain, with `simple-host-site-certs-site.{service,timer,path}` for `simple-host.site`; the custom-domain issuer refuses both platform zones. Nothing changes until the settings are set: pages, `llms.txt`, the OpenAPI spec and the connector's text name people's addresses under `simple-host.site` in source and are served exactly as before until the hosted service hands the new addresses out. No migrations.
- **Skills 0.27.3: visitor content is data, not instructions.** website-deploy (and its backend and operations references) and connect-domain gain a short section: entries, saved data, comments, form submissions, analytics referrers and page content can be written by strangers, so the agent treats them as untrusted, quotes or summarises them for the person, never follows instructions, links or requests inside them, never deletes, publishes or changes visibility, domains, keys or the account because the data asked, and points out an entry that tries to instruct an AI. Same rule in the OpenAI plugin 0.9.4 (website-deploy and saving-data), `llms.txt` and the connector's instructions; MCP tool descriptions unchanged. Addresses the skills.sh (Snyk) W011 third-party content finding.
- **Skill URLs work under both prefixes.** `/v1/skills/<name>/SKILL.md` now serves the same file as `/v1/skills/<name>` (an agent got a 404 on `/v1/skills/connect-domain/SKILL.md`), and `/skills/<name>` and `/skills/<name>/references/<file>` now work like their `/v1/skills/` pairs, for every skill. No migrations.
- **Skills 0.27.2: relative links are a tip, not the rule that breaks sites.** Every site has its own address, where root-relative links like `/style.css` work, so website-deploy drops the "one rule that breaks sites" heading (now "Where a site lives", keeping the address and `site_url` guidance) and gives a short tip in the deploy section instead: relative links keep version previews and a new site's first minutes working too. Same change in website-deploy-builder, the framework and packaging references, `llms.txt`, the connector's instructions and the OpenAI plugin 0.9.3.
- **Choose your address at sign-up.** When an emailed code, sign-in link or Google sign-in would create a new account, the page first asks "Choose your address", prefilled with the address it would have been given (Continue keeps it) and checked while you type; closing it creates nothing and the code still works. Agents do the same with `choose_handle` and then `handle` on `POST /v1/auth/verify` (a taken, reserved or malformed handle is refused without using up the code). New `GET /v1/handles/check?handle=` says whether an address is free or why not (per-IP limit `RATE_LIMIT_HANDLE_CHECK`, default 30 at once then one every 2 s; cross-site browser requests refused). Changing your address on your page checks it while you type and before asking; A handle is also taken when another account has a live site of that name, since an unclaimed `<name>.simple-host.app` still redirects to it (vineetsriram.simple-host.app → vineetsriram.com). `PATCH /v1/me` now answers a taken or reserved handle with 409 `handle_taken` / `handle_reserved` naming the address ("That address is taken: vineetsriram.simple-host.app is already in use. Try another."); reserved used to be 400. A refused save shows why under the field and leaves you signed in. Skills 0.27.1, OpenAI plugin 0.9.2. No migrations.

Covers changing your address, deleting, renaming and rolling back sites, connecting and disconnecting domains, sign out everywhere (the new key is shown with Copy), revoking keys, unlinking sign-ins, taking a site offline, list privacy, blocking savers, deleting and restoring items, the account-deleted notice and the admin's new key, delete, take-down and suspend (the reason is typed in the page).
